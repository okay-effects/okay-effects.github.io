Scala and Spark: from tangled code to one transparent, controllable system.

I have spent years in Scala and Spark codebases, and I know where they hurt. The code is hard to read and seems impossible to improve or move to new versions. The ecosystem is split between ZIO, Cats and the rest. Monitoring, control and audit are hard, and hardest for Spark jobs. This page names those problems and shows how I solve them: by making what the code does explicit, one part at a time, until systems on different platforms, and even in different languages, become one system that can be watched and controlled.

The problems everyone has with Scala and Spark today

None of these is anyone's fault. They are what years of growth do to a codebase and to an ecosystem.

Code

Tangled code nobody dares to touch

Implicits several layers deep, stacks of monad transformers, business logic mixed with I/O, and Spark jobs thousands of lines long. It works, but nobody can say what it does without running it. Moving it from Scala 2.12 to 2.13 or 3, or from Spark 3 to 4, looks like a rewrite, so it does not happen.

Ecosystem

Fragmented solutions

ZIO, cats-effect, Future, kyo and monix each bring their own effect type, their own way of handling errors and resources, and their own community. A company ends up with several of them in one system, glue code between them, and teams that cannot read each other's code.

Operations

Monitoring and control are bolted on

What a service calls, what a job reads and writes, which external systems it reaches: all of this is reconstructed from logs, metrics and listeners added afterwards. Changing a policy, such as a limit, a retry or a masking rule, means changing the code everywhere.

Spark

Spark jobs are the hardest to audit

The event log says that a job ran. It does not prove what the job produced. Tests need a Spark session, so the logic is tested late or not at all. Scala 3 types do not fit Spark's encoders, which pushes teams to stay on old versions.

Across the company

Many platforms, many languages, no common control

JVM services, Python data science, Go and Rust services, a TypeScript front end. Each has its own way of calling the world, so there is no single place to see, limit or audit what the whole system does.

What I offer

One idea runs through all of it. What code does to the world (a call, a read, a write, a payment, a model query) becomes an explicit operation, and a handler carries it out. That gives each action a place where it can be seen, tested, controlled and recorded, and the logic around it stays as it is.

1. A way out of tangled code, one step at a time

Wrap the code's dependencies as effects at its existing seams. The logic keeps its shape and becomes testable with handlers instead of mocks and containers. Then improve it piece by piece, and split it into services along the same boundaries when that pays. okay-simple is one interface for Scala 2.13 and Scala 3, from 3.3 LTS on. One application can mix code compiled by both, so an upgrade happens module by module, not in one big step.

2. One interface over ZIO, Cats, kyo, fs2 and monix

Teams keep their libraries. Business logic is written once against effects, and each library is an interop module. A ZIO's environment, typed error and run become standard effects, with its layers and cancellation in both directions. cats gets a Monad of programs, and a program runs as cats-effect's IO. kyo computations, fs2, ZIO and monix streams convert both ways. With ZIO, its own types can be effects, accumulated as ZIO itself would:

// ZIOs of different environments and errors, each its own effect, in one program
type Row[X] = (ZioStep[Db, DbErr] + ZioStep[Log, LogErr])[X]

val program: Int ! Row =
  for
    a <- ZIO.serviceWith[Db](_.n).step[Row]
    b <- ZIO.serviceWith[Log](_.tag.length).step[Row]
  yield a + b

val asZio: ZIO[Db & Log, DbErr | LogErr, Int] = program.toZIOSteps   // back to ZIO, typed as ZIO would

With Cats, cats code written for any Monad runs on effect programs, and cats-effect's IO goes into a program and comes back out as an IO:

import cats.Monad
import cats.effect.IO
import cats.effect.unsafe.implicits.global
import okay.effects.catsinterop.*

// cats code, written for any Monad, runs on effect programs
def twice[F[_]: Monad](fa: F[Int]): F[Int] = Monad[F].flatMap(fa)(a => Monad[F].map(fa)(_ + a))

type Counter[X] = (State % Int)[X]
val counted: Int ! Counter = twice[Program[Counter]#L](modify[Int, Counter](_ + 1).andThen(get[Int, Counter]))
run(state(0)(counted))                       // (2,3)

// cats-effect's IO inside a program, and the program back as an IO
type InIO[X] = Lift[IO, X]
val both: Int ! InIO =
  for
    a <- lift[IO, Int, InIO](IO(20))
    b <- lift[IO, Int, InIO](IO(a + 22))
  yield b
lower[IO, Int](both).unsafeRunSync()         // 42

Both blocks were compiled and run against the released 0.1.0 (okay-effects-zio, okay-effects-cats) on Scala 3.3 and 3.9. kyo, fs2 and monix work the same way: see interop.

3. Spark you can test in one JVM and prove on a cluster

A Spark job written against Bulk runs on a cluster or in one JVM with the same answer, so its logic is tested without Spark. Scala 3 types become DataFrames through SparkSchema. Every output can come with evidence: per partition, a count and a SHA-256 digest, committed only after the sink acknowledges it. The details are below.

4. Monitoring, control and audit as part of the code

An interceptor sees each operation of an effect and can record, change or refuse it. An observer sees every operation of every effect. A sensitive effect, such as payments, cannot run outside its audit, and the compiler checks that. okay-audit checks in the bytecode, at every build, that business code reaches the outside world only through declared effects. A policy is changed in one handler, not across the codebase. See what this means for compliance.

5. One transparent system across platforms and languages

The same design exists for Java, Go, Rust, Python and TypeScript. okay-kernel is a protocol between them: a program written in one language runs under handlers written in another, in one process or over a wire. In the demo, a shop written in Go has its inventory, payments and mail answered by Scala handlers. Every operation that crosses has a name and a type, so the controls above apply to it wherever it came from. The whole company's software can be watched, limited and audited at one point.

Spark in detail

One aggregation, local or distributed

An okay Aggregator (init, add, merge, present) maps onto Spark's zero, seqOp and combOp. The same value runs over a local collection, over an RDD, per key, or as a Dataset column. It is written and tested once.

import okay.spark.SparkInterop.*

val stats = Aggregator.mean[Double].zip(Aggregator.variance[Double])

val (m1, v1) = stats.run(data)                              // locally
val (m2, v2) = aggregate(sc.parallelize(data, 8))(stats)    // the SAME value, distributed
val byKey = aggregateByKey(pairs)(Aggregator.variance[Double])
ds.select(toSpark(stats).toColumn)                          // as a typed Dataset column

One program, a cluster or one JVM

A job written against Bulk[D] does not name its platform. On SparkBulk it is a cluster job. On localBulk it runs in one JVM and gives the same answer, which is how it is tested. okay's own tests check the two against each other.

def revenue[D[_]](using B: Bulk[D]) =
  B.csv("sales.csv").map(r => r("shop") -> r("amount").toLong)
    .join(B.csv("shops.csv").map(r => r("id") -> r("city")))
    .aggregate(Aggregator.groupBy((kv: (String, (Long, String))) => kv._2._2)(
      Aggregator.sum[Long].contramap(_._2._1)))

revenue(using SparkBulk(spark))   // a cluster
revenue(using okay.localBulk)     // one JVM, the same answer

Scala 3 types as DataFrames

SparkSchema turns an okay Schema[A] into a StructType and rows. That covers Scala 3 enums, which Spark's ExpressionEncoder does not see:

  • A pure enum becomes its case name.
  • A sum with payloads becomes a tagged sparse struct, so a new case is a new nullable column and old Parquet still reads.
  • A recursive type becomes lossless CBOR plus a Spark 4 VARIANT.
val df = SparkSchema.dataFrame(spark, Seq(
  Output(1, Credential.KeyHash(Array[Byte](1)), BigInt(2_000_000)),
  Output(2, Credential.ScriptHash(Array[Byte](2)), BigInt(5_000_000))))
// owner: struct<kind: string, KeyHash: struct<hash: binary>, ScriptHash: struct<hash: binary>>
df.createOrReplaceTempView("outputs")
spark.sql("SELECT id, lovelace FROM outputs WHERE owner.kind = 'ScriptHash'").collect()
// Array([2,5000000])

Catalyst where it counts

With SparkFrames, a DataFrame-born table stays in Catalyst while it meets only structural operators: a predicate becomes a Column (a pushed filter on Parquet), and a join becomes a DataFrame join.

Sketches as aggregators

HyperLogLog, count-min and quantiles (okay-data) are aggregators, so approximate distinct counts and percentiles run distributed with no extra code.

Delta Lake without Spark

okay-delta creates tables and appends to them through delta-kernel. Its loadId uses Delta's transaction identifier, so a load lands once even when it is retried. A small producer needs no cluster.

Audit in Spark: evidence of what was written

Spark's event log and listeners record what ran: jobs, stages, task times. They do not prove what came out. SparkEvidence does. For each partition it records the partition's id, its successful task attempt, its row count and a length-framed SHA-256 digest of its records. It folds these into a run digest and hands the manifest to your sink. The result is Committed only after the sink has durably committed and acknowledged.

object SparkEvidence:
  trait Canonical[-A] extends Serializable:
    def bytes(value: A): Array[Byte]          // a record's deterministic bytes: yours

  final case class Partition(id: Int, attempt: Long, count: Long, digest: String)
  final case class Manifest(runId: String, partitions: Vector[Partition], digest: String)
  final case class Receipt(output: String, acknowledgement: String)
  final case class Committed(manifest: Manifest, receipt: Receipt)

  def run[A](rdd: RDD[A], runId: String)(canonical: Canonical[A])(sink: Manifest => Receipt): Committed

In use:

// a sketch: the canonical encoding and the sink are the application's
val committed = SparkEvidence.run(trades, runId = "eod-2026-10-18")(tradeBytes) { manifest =>
  evidenceStore.commit(output = "s3://ledger/eod/2026-10-18", manifest)   // durable first, then a receipt
}
// committed.manifest.partitions: one (id, attempt, count, SHA-256) per partition
// committed.manifest.digest:     the run's digest — the same input, the same digest

Reproducible

The same input, partition layout and record order give the same digest, so rerunning the job proves that the output is the same. Attempt ids are kept for diagnosis and never choose a winner.

No acknowledgement, no evidence

A failed sink produces no Committed value, so evidence never claims an output that was not stored. Empty partitions are counted too.

No data in the logs

Only counts and digests leave the tasks. Payloads and credentials do not enter task logs.

Around the job: its reads and writes as effects

With SparkFrames, loading, reading and handing back a DataFrame are effects of the program. The audit-by-construction pattern then applies to a Spark job as it does to a bank. A handler around them records each dataset read and written, intent first and result after, and the job's code does not change. Together with the evidence manifest this answers the questions an auditor asks: what went in, what came out, and whether it can be shown to be the same again.

Durable storage, identity and access, signatures and regulatory policy stay with the application. The adapter commits summaries and does not claim atomicity with a separate Spark write. An application that needs both provides a sink that commits output and manifest in one transaction.
